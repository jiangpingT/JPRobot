## 关键备忘

### 速度奖励修复的本质

> 旧版 sigma=0.25 + 零速命令 → 站着不动就能得 93% 满分 → 机器人爬行骗分
> 新版 sigma=0.15 + fixed_vel_cmd=[0.25,0] → 站着只能得 66% → 被迫真正往前走

**数学推导**：
```
standing_reward = exp(-cmd_norm² / sigma)

旧版：cmd=[0.25,0], sigma=0.25 → exp(-0.0625/0.25) = exp(-0.25) ≈ 0.78  → 78% 满分
      cmd=[0.05,0], sigma=0.25 → exp(-0.0025/0.25) = exp(-0.01) ≈ 0.99  → 99% 满分（零速骗分）

新版：cmd=[0.25,0], sigma=0.15 → exp(-0.0625/0.15) = exp(-0.42) ≈ 0.66  → 66% 满分
      vel_cmd_min_norm=0.15 → 不再抽到近零命令
```

两个修复缺一不可：① sigma 降低 ② fixed_vel_cmd bootstrap 阶段

### Route A 向后崩溃的 Reward Hacking

> 当目标=向后，前进动作 → 大负奖励；快速摔倒 → reward=0。
> ent_coef=0.0 情况下，摔倒比尝试后退更"合算"，机器人学会了"收到向后指令就倒下"。

修复思路：`ent_coef=0.015` 强制探索 + `backward 概率=55%` 大量暴露后退 episode

### Route B 向后改善的尝试（全部失败）

| 方案 | 做法 | forward 结果 | backward progress | 失败原因 |
|------|------|-------------|-----------------|---------|
| 激进 bootstrap | fixed_vel_cmd=[-0.20,0], ent=0.015, 400k步 | 934（崩溃） | 无改善 | 灾难性遗忘：400k步洗脑向后，忘记向前 |
| 保守范围限制 | range_x=[-0.35,-0.10], ent=0.003, 500k步 | 维持 1224 | 无改善（0.00017） | 奖励软地板：梯度信号太弱，无法发现新步态 |
| Route B v3（feet_air_time） | 从零重训，+alive bonus，obs=254，2.5M步 | 1238（微升） | 无改善（0.00014） | feet_air_time 方向无关，前进步态仍主导梯度 |

**根本结论**：`exp(-error²/σ)` 的奖励结构决定了梯度方向模糊。慢速原地颤抖可得 60-80% 满分，优化器无动力探索全新的向后步态。feet_air_time 无法解决这一结构性问题，因为机器人可以用前进步态抬腿获得 air_time 奖励，而不管速度命令指向哪个方向。

**Route B 真实定位**：擅长向前行走 + 多方向存活（不摔），但实际只有向前真正移动。

### Route B 侧向/后向不移动的原因

- 课程设计过度偏重向前（1.5M 步前向训练）
- 最后 1M 双向阶段 `ent_coef=0.0`，策略彻底固化，无法探索新步态
- 机器人找到"慢速伪匹配"：以近零速缓慢移动，每步误差小 → 约 80% 追踪奖励，不需要学真正的后退步态
- 修复：对后退方向做专项 `fixed_vel_cmd=[-0.20, 0.0]` bootstrap

## SOTA 课程迁移实验（2026-02-22）

### 核心发现：无 Bootstrap 原则不适合 12 并行环境

从 legged_gym / unitree_rl_gym 学到三个 SOTA 原则，但迁移结果参差不齐：

| SOTA 原则 | 在我们这里有效？ | 原因 |
|----------|--------------|------|
| 无前向 bootstrap，第1步全方向 | ❌ 更差 | 12 envs 梯度噪声太大，4096 envs 才能无 bootstrap |
| only_positive_rewards（奖励截断≥0） | ✅ 有效 | 根治 Route A 向后 reward hacking（ep_len 42→251） |
| episode 250→500步 | △ 中性 | 更长 episode 但总步数减少，净效果不明显 |

**核心结论**：Bootstrap 课程本质上是**方差降低（Variance Reduction）**手段——在少并行环境下，先简化问题让梯度信号强，再逐步引入难度。SOTA 用 4096 并行环境消除了这一需求，我们的 12 环境不能直接照搬。

### 全实验对比表（确定性推理，20局/方向）

| 模型 | 步数 | 前进进度 | 后退ep_len | 左 | 右 | 手臂触地 | 核心问题 |
|------|------|---------|-----------|----|----|--------|---------|
| Route A 旧版 | 5M | **0.00576** | 42（崩溃） | 0.00437 | 0.00495 | 低 | 向后 hacking |
| Route B v2 | 2.5M | 0.00290 | 251 | 0.00036 | 0.00054 | 0% | 不真正移动 |
| Route A SOTA | 3M | 0.00427 | 251（不崩） | 0.00258 | 0.00398 | 中 | 全面弱于旧版（步数少+无bootstrap） |
| Route B v3 | 2.5M | 0.00248 | 251 | 0.00025 | 0.00092 | 高 | feet_air_time 方向无关，无效 |
| Route B SOTA | 3M | **≈0**（ac=84%） | 251 | ≈0 | ≈0 | **84%** | 灾难：机器人学会爬而非走 |

**Route B SOTA 失败原因（最严重）**：
- 无 bootstrap → 从未学会基本前进步态
- sigma=0.25（宽松）+ alive bonus → 站立/爬行即可得 80% 奖励
- 机器人找到新的 local minimum：四肢撑地爬行（arm_contact=84%），获得 alive bonus + 部分速度奖励
- 本质上是更复杂的骗分方式：不是"站着不动"，而是"爬着不走"

**最优策略确认**：Route A 旧版（5M步，bootstrap课程）是当前最好的起点，只差一个修复：`only_positive_rewards` 解决向后 reward hacking。

## SOTA 代码对比：防爬行机制（2026-02-22）

### Route B SOTA 爬行失败根因（arm_contact=84%）

爬行 Local Minimum 形成链条：
```
无 bootstrap（未先学前进步态）
    + sigma=0.25（软）→ 趴着不动可得 78% 奖励
    + alive bonus=+0.2/step → 趴着活着 = 稳定收益
    + arm_contact penalty=0.01（弱）→ 手臂触地几乎免费
= 趴着爬行得 80% 奖励，优化器找到新 local minimum
```

### 三个 SOTA 框架的防爬行机制

| 机制 | legged_gym A1 | unitree H1 | opencat-gym | 我们 |
|------|--------------|-----------|------------|------|
| 躯体接触终止 | ✅ base touch > 1N → reset | ✅ base touch → reset | ❌ 无 | ❌ 无 |
| 倾角终止 | ❌ 无 | ✅ `\|roll\|>0.8, \|pitch\|>1.0` → reset | `\|orient\|>1.3` → reset | `\|orient\|>1.3`（宽松） |
| 接触惩罚系数 | -1.0（thigh, calf） | -1.0（hip, knee） | -0.01（arm） | **-0.01（弱 100x）** |
| alive bonus | ❌ 无 | ✅ 但有倾角终止保护 | ❌ 无 | ✅ 无保护（危险）|
| 躯体高度惩罚 | -0（禁用） | **-10.0（强）** | 无 | 无 |

### 最关键的缺失机制：硬终止

legged_gym 代码（legged_robot.py:138）：
```python
# 躯体接触地面 → 立即 reset
terminate_after_contacts_on = ["base"]
self.reset_buf |= torch.norm(contact_forces[:, base_indices, :], dim=-1) > 1.
```

unitree H1（legged_robot.py:122）：
```python
# 侧倾 > 45° 或俯仰 > 57° → 立即 reset（防止趴下爬行）
self.reset_buf |= torch.logical_or(abs(rpy[:,1]) > 1.0, abs(rpy[:,0]) > 0.8)
```

我们的 `is_fallen()` 阈值是 `1.3 rad（74°）`——机器人可以安全趴着爬行而不触发终止。

### Route B 防爬行修复方案（待实施）

1. **高度终止**：`avg_height < 0.04m → terminate`（等效于躯体接触地面）
2. **接触惩罚**：`FAC_ARM_CONTACT` 从 0.01 提高到 0.05~0.10
3. **移除 alive bonus**（或改为高度加权：`alive_reward = height / height_target`）
4. **保留 forward bootstrap**（不能跳过，12 envs 需要方差降低）

**物理瓶颈**：高度 0.32m → 腾空时间 ~0.51s，当前角速度 ~150°/s，目标需要 ~560°/s（差 4 倍）。差距必须在起跳时（地面接触阶段）解决，腾空后角动量守恒无法增加。

### 各版本迭代逻辑

| 迭代 | 核心改动 | 结论 |
|------|---------|------|
| V1→V2 | 落地加 90° 旋转门槛，W_ROTATION 5→15 | 堵死落地 gaming |
| V2→V3 | 加里程碑奖励，删角速度 gaming 奖励 | 堵死振荡 gaming，但地面 gaming 仍存在 |
| V3→V4 | W_SPIN_AT_LAUNCH=0，删 jump 阶段，从 V2 full 热启动 | **首次真实腾空（35cm）**，但切断了角动量信号 |
| V4→V5 | 加 W_ROT_STEP=2.0（腾空单调增量奖励），从 V4 full 热启动 | 无效，空中无法增加角动量 |

### V3 的 `vz > 0` 条件为何不够用

V3 代码里 `W_SPIN_AT_LAUNCH` 的门槛已经是 `vz > 0 and not self._airborne`，但仍被 gaming：地面蹬腿时 vz 就已经 > 0（腿在推地），机器人可以贴地后仰同时蹬腿，持续拿奖励但从不真正起跳。

**正确的门槛**：`_airborne` 从 False 变 True 的边沿（腾空第一帧），此时机器人已物理上离地，无法在地面触发。

### DeepMimic 后空翻关键发现

> 来源：`bullet3/examples/pybullet/gym/pybullet_envs/deep_mimic/`
> 参考运动：`pybullet_data/data/motions/humanoid3d_backflip.txt`（28帧，1.75s）

**1. 没有显式角动量奖励**
奖励完全是运动模仿（pose + velocity + end-effector + root 位置），通过 `vel_reward = exp(-0.1 × Σ角速度差²)` 间接要求 agent 产生参考运动指定的角速度。

**2. 角动量在地面就开始建立（关键！）**

| 帧 | 时间 | 状态 | pitch 角速度 |
|----|------|------|-------------|
| 4 | 0.25s | 蹲伏中，脚仍着地 | **-90°/s** |
| 5 | 0.31s | 持续蹲伏，脚仍着地 | **-111°/s** |
| 8 | 0.50s | 最低点（膝弯 87°） | +308°/s（蹬腿爆发）|
| 11 | 0.69s | 腾空上升（vz=2.98m/s）| -30°/s |
| 17 | 1.06s | 最高点（1.18m，已转 203°）| -226°/s |

**后空翻角动量三步走**：① 地面蹲伏阶段预旋（0.5s 积累） → ② 最低点爆发蹬腿（0.0625s 内产生最大冲量） → ③ 腾空后收腿减小转动惯量（I↓ → ω↑，角动量守恒）

**3. RSI（Random State Initialization）**
每个 episode 从参考运动的随机帧开始，包括旋转到一半的空中状态，让 agent 可以直接练习旋转阶段，不用每次从 0 发现翻转行为。我们完全没有这个机制。

**4. 训练规模差距**
- 网络：2×1024（vs 我们的 256×256）
- 学习率：0.0000025（vs 我们的 3e-4，大 120 倍）
- 总步数：32M+（vs 我们每版本 5M）

### V6 改动方向（优先级排序）

| 优先级 | 改动 | 原理 |
|--------|------|------|
| ★★★ | 腾空第一帧一次性角速度奖励（`_airborne` 边沿触发） | 直接奖励起跳时实际角动量，无法 gaming |
| ★★★ | RSI：rotate 阶段随机初始化到已腾空/旋转中的状态 | 解决探索效率问题，让 agent 直接练旋转阶段 |
| ★★ | W_POSE_GUIDE 1.5 → 4.0 | 强制腾空后折叠腿，放大已有角动量（I↓ → ω↑）|
| ★★ | MOTOR_FORCE 2.0 → 3.5 | 允许更强蹬腿冲量，可能是当前物理上限 |
| ★ | rotate 阶段步数 2M → 4M | 角动量行为收敛需要更多时间 |

腾空第一帧奖励伪代码：
```python
if self._airborne and not self._was_airborne_prev:
    backward_ang = max(0.0, -ang_vel[1])
    reward += W_SPIN_AT_LAUNCH_ONCE * backward_ang  # 只触发一次，无法 gaming
self._was_airborne_prev = self._airborne
```

#### V6 核心 Bug：W_SPIN_AT_LAUNCH_ONCE 权重过大

**Gaming 机制**：
```
奖励 = W_SPIN_AT_LAUNCH_ONCE × backward_ang
     = 20.0 × 15 rad/s
     = 300 分（单步）
```

- `W_SPIN_AT_LAUNCH_ONCE = 20.0`：奖励权重（我们设置的）
- `backward_ang ≈ 15 rad/s`：腾空瞬间向后角速度（MOTOR_FORCE=3.5 让 agent 能产生）
- 300 分远大于旋转里程碑（W_MILESTONE × W_ROTATION ≈ 3×20=60 分/里程碑）和落地奖励

**Agent 学到的策略**：
1. 起跳时猛地后仰，让 ang_vel 飙到 -15 rad/s → 拿 300 分
2. 腾空后不在乎旋不旋完整 → ep_len 仅 31 步就结束
3. height 从 rotate 的 0.363m 降到 full 的 0.282m（蹬腿力量全用来产生角速度，垂直速度变少）

**诊断依据**：
- V6 full 比 V6 rotate 旋转退步（70.8° vs 72.6°）
- V6 full 所有 20 局完全相同 → 策略已固化在"飙角速度"这个 local optimum
- ep_len=31（极短），说明 agent 快速完成腾空→拿奖励→倒地全流程

### V7 修复方案（2026-02-23）

**核心原则**：对 `backward_ang` 加上限（cap），让极端角速度与正常角速度奖励相同，倒逼 agent 靠旋转里程碑赚后续奖励。

#### 参数变更

| 参数 | V6 | V7 | 理由 |
|------|----|----|------|
| `W_SPIN_AT_LAUNCH_ONCE` | 20.0 | **10.0** | 降低一次性奖励绝对值 |
| `backward_ang` cap | 无限制 | **min(backward_ang, 5.0)** | 超过 5 rad/s 不再有额外收益 |
| 最大一次性奖励 | 20 × 15 = **300** | 10 × 5 = **50** | 里程碑奖励（60分）> 一次性奖励，策略方向扭转 |
| 课程 | rotate 4M + full 3M | 保持不变 | 已够用 |
| 热启动 | V5 full → V6 | V6 full → V7 | 保留 V6 的 RSI 多样性 |

#### 为什么 cap=5 rad/s

正常后空翻的腾空角速度大约 3–6 rad/s（DeepMimic 参考数据帧 11 显示 -30°/s ≈ 0.5 rad/s，但峰值在地面）。Cap 设 5 rad/s 是对"合理范围内的强烈后翻"的奖励上限，不阻止正常翻转，只截断 MOTOR_FORCE=3.5 产生的异常 15 rad/s。

#### V7 奖励结构对比

```
V6 gaming 路径：一次性 300分 >> 里程碑 60分 × 3 = 180分
V7 正确路径：  一次性  50分 << 里程碑 60分 × 3 = 180分
```

V7 中，要拿最多奖励必须真正完成 90°/180°/270° 三个旋转里程碑，一次性奖励只是"起跳奖金"，不再是主要收入来源。

### 一、课程阶段哪些必要，哪些可以删

| 阶段 | 必要性 | 结论 |
|------|--------|------|
| jump | 否 | V4 起删掉后效果更好；RSI 已能让 agent 接触腾空状态，不需要单独学起跳 |
| rotate | **核心，必须** | 后空翻的真正瓶颈，所有 8 版本都卡在这里（60-87°，从未过 90°）|
| land | 否 | 落地奖励本身是 gaming 高危区（V1 教训），增加这个阶段只增加 gaming 风险 |
| full | 保留但意义有限 | 因为 rotate 没突破 90°，full 的落地/站稳/成功奖励全部无法触发，等于只是继续 rotate |

**规律**：课程阶段越多，每个阶段的 gaming 风险越高，维护成本越高。在当前瓶颈下，只需要 rotate + full 两阶段。

### 二、5 种 Gaming 模式总结（必须牢记）

| 版本 | Gaming 类型 | 表现 | 修复方式 | 是否彻底修复 |
|------|------------|------|---------|------------|
| V1 | 落地无门槛 | 跳不翻直接落地拿奖励 | ROTATION_GATE=90° | ✅ 是 |
| V2/V3 | 地面贴地后仰 | 趴地后仰 82° 拿 W_SPIN_AT_LAUNCH，但从不起跳 | `_airborne` 边沿检测（height>12cm）| ✅ 是 |
| V2/V3 | 空中振荡角速度 | 正转反转振荡，瞬时 ang_vel 高但净旋转 60° | 里程碑一次性奖励（不可重复）| ✅ 是 |
| V6→V8 | 腾空一次性奖励飙角速度 | 起飞瞬间 ang_vel 飙到 15-29 rad/s 拿高分，之后摆烂 | cap + 降权重 + 降 MOTOR_FORCE | **❌ 未修复** |
| V5/V6/V8 | 策略固化 | 20 局完全相同，旋转一致性 ±0° | RSI（rotate 阶段有效）| 部分（full 阶段仍固化）|

**最关键教训（V6→V8 的核心发现）**：
> **任何与起飞角速度线性相关的奖励（`reward = W × ang_vel`），无论权重大小、是否加 cap，都无法避免 gaming。**
>
> 原因：cap 截断的是奖励，不截断行为动机。只要 W > 0，优化器就会把 ang_vel 推向 cap 上限。
> 降低 MOTOR_FORCE 只是物理限制，但 agent 通过时序控制和姿态协调仍能产生极端角速度（V8 用 2.0 N·m 仍达 26.8 rad/s）。
> 热启动继承了 gaming 行为，越传越强，V6 是 15 rad/s，V7/V8 反而变成 29 rad/s。

### 四、热启动策略的代价

每一代从上一代热启动是好事（继承基础行为），但有隐患：

- **如果上一代有 gaming 行为，热启动会继承并放大 bug**
- V6 起飞ω=15 → V7=29 → V8=26.8，gaming 行为越传越根深蒂固
- **规律：当发现根本性 gaming 时，应从更早的干净模型热启动**（如 V4 rotate，干净的真实腾空但无 gaming）

### 五、物理瓶颈（最根本的问题）

```
目标：旋转 270°，腾空时间 ~0.5s（h=0.28m → 飞行时间 ≈ 2√(0.28/9.81) ≈ 0.48s）
需要平均角速度：270° / 0.48s = 562°/s ≈ 9.8 rad/s

当前实际旋转角速度：75° / 0.48s ≈ 156°/s ≈ 2.7 rad/s

差距：~4 倍
```

这 4 倍差距必须在地面起跳阶段积累（角动量守恒，腾空后无法增加）。DeepMimic 的正确三步走：
1. **地面蹲伏预旋**（0.5s，脚着地时 ang_vel 就达到 -90 ~ -111°/s）
2. **最低点爆发蹬腿**（0.06s 内产生最大向上+向后冲量）
3. **腾空收腿**（减小转动惯量 I，由 L=Iω 守恒 → ω 放大）

我们当前的奖励函数激励的是"腾空瞬间角速度"，而不是"地面蓄力过程"。这是方向性错误。

**可选改变（次优先）：**

## Backflip V12-V15：旋转卡 60° 根因排查（2026-02-24）

### 一、问题描述

V9-V11 经过多轮优化后，旋转量始终卡在 63-67°，`pct_over_90deg = 0%`。
提高 MOTOR_FORCE（2→3→4 N·m）、提高 MOTOR_VELOCITY（10π→20π）、修复奖励方向（abs→max(0,-)）……14 个版本，全部失败。

### 二、排查过程（时间轴）

| 版本 | 假设 | 实验 | 结论 |
|------|------|------|------|
| V12 | MOTOR_VELOCITY 是瓶颈，提高到 20π | liftoff ω 从 +6.67 变 -8.97（前空翻！） | 方向反了，abs() 奖励无向性 |
| V13 | 修复奖励方向（abs→max(0,-)） + 15π | liftoff ω=+15 r/s，方向正确，仍 65° | 高 ω 但低旋转，效率仅 16% |
| V14 | POSITION_CONTROL 在空中阻尼角动量 | 腾空零力矩（forces=0），旋转 63.5°（更差）| 零力矩假说证伪 |
| **V15** | **Euler 万向锁** | **角速度积分** | **45% 超过 90°，30% 超过 180°** |

### 三、根因：ZYX Euler 角万向锁（Gimbal Lock）

**物理过程：**

PyBullet 的 `getEulerFromQuaternion()` 使用 ZYX 分解：
```
pitch = arcsin(2 × (qw×qy − qz×qx))
```
当 `pitch = ±90°` 时，上式分母趋于零，pitch 和 yaw 退化为同一自由度（奇异点）。

**为什么偏偏卡在 60-70°？**

后空翻从 0° 旋转到 90° 的过程中，机器人同时有轻微横滚（roll ≈ 20-40°）。当 roll 不为零时，Euler 奇异性会在 pitch 略小于 90° 时提前触发。在 60-70° 区间，`d_pitch = pitch - prev_pitch` 的差分开始产生错误跳变，奖励信号崩溃，agent 在这个区间附近永远得不到清晰的正向梯度。

**诊断线索（事后验证）：**
- 训练奖励：V15 训练中 ep_rew 达到 200-280（vs V13 的 118），说明里程碑奖励首次被触发
- 评估突破：V15 rotate `pct_over_90deg = 45%`，`pct_over_180deg = 30%`
- 之前 14 个版本：这两个指标全部为 0%，即使 liftoff ω 从 6.67 提高到 15 r/s 也没变化

### 四、修复：角速度积分替换 Euler 角差分

```python
# 旧方法（V1-V14，有万向锁）：
d_pitch = pitch - self._prev_pitch
if d_pitch >  math.pi:  d_pitch -= 2 * math.pi
if d_pitch < -math.pi:  d_pitch += 2 * math.pi
self._pitch_accumulated += d_pitch

# 新方法（V15，无奇异性）：
# ang_vel[1] = p.getBaseVelocity() 返回世界坐标系 Y 轴角速度
# 世界坐标下的角速度没有 Euler 奇异性，积分永远准确
self._pitch_accumulated += ang_vel[1] * _DT   # _DT = PHYSICS_STEPS / 240.0
```

`ang_vel` 来自 `p.getBaseVelocity()`，在**世界坐标系**下表达，不受 Euler 分解影响，可以准确穿越 90°/180°/270° 所有里程碑。

### 五、实验数据对比

| 版本 | mean_rot | pct>90° | pct>180° | liftoff ω |
|------|---------|---------|---------|-----------|
| V9 | 67.4° | 0% | 0% | +7.41 r/s |
| V11 | 63.0° | 0% | 0% | +6.67 r/s |
| V13 | 66.9° | 0% | 0% | +15.0 r/s |
| V14 | 63.5° | 0% | 0% | +12.53 r/s |
| **V15 rotate** | **100.8°** | **45%** | **30%** | **+14.24 r/s** |

### 七、通用教训

**对所有使用 Euler 角的 RL 项目：**

1. **永远不要用 Euler 角差分追踪大角度旋转。** 尤其是翻滚/空翻类任务，旋转必然经过奇异点。
2. **用角速度积分代替 Euler 差分**：`θ += ω × dt`，准确、简单、无奇异性。
3. **或者用四元数对数映射**：`q_rel = q_prev⁻¹ × q_now`，提取旋转轴角度，同样无奇异性。
4. **诊断 gaming 的快速方法**：比较 `mean_liftoff_ang_vel` 和 `mean_max_rotation_deg` 的物理一致性。如果 ω 高但旋转低（效率 < 20%），说明奖励信号失真，而非物理限制。
5. **Silent bug 最难排查**：代码逻辑没错、物理真实、没有 NaN/报错，只有一个不起眼的指标（旋转卡在固定值）。这类 bug 需要从物理学出发提出假设，而不是从代码逻辑出发。
